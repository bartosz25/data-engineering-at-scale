# Project 08: London Tube Live Arrivals (Transport for London)

## Overview

Transport for London (TfL) exposes a free REST API that returns real-time train
arrival predictions for every station on the Underground, Overground, DLR, and
Elizabeth line. Each station endpoint returns the next ~20 trains expected in the
next 30 minutes, updated every 30 seconds.

Your pipeline polls a fixed set of central London stations, validates the data,
and builds a **platform headway monitor** — a measure of how evenly trains are
spaced throughout the day.

## Data Source

| Property | Value |
|----------|-------|
| URL | `https://api.tfl.gov.uk/StopPoint/{naptanId}/Arrivals` |
| Protocol | REST (GET, JSON response) |
| Auth | None required (rate limit: 500 requests/minute) |
| Poll interval | Every 30 seconds |
| Format | JSON array of arrival prediction objects |

## Key schema fields

```json
{
  "id": "1038491162",
  "operationType": 1,
  "vehicleId": "225",
  "naptanId": "940GZZLUOXC",
  "stationName": "Oxford Circus Underground Station",
  "lineId": "central",
  "lineName": "Central",
  "platformName": "Westbound - Platform 1",
  "direction": "inbound",
  "bearing": "",
  "destinationNaptanId": "940GZZLUEAC",
  "destinationName": "Ealing Broadway Underground Station",
  "timestamp": "2024-01-15T10:30:00Z",
  "timeToStation": 237,
  "currentLocation": "At Marble Arch",
  "towards": "Ealing Broadway",
  "expectedArrival": "2024-01-15T10:33:57Z",
  "timeToLive": "2024-01-15T10:34:27Z",
  "modeName": "tube"
}
```

Key fields:
- `id` — unique prediction ID for this specific train at this station
- `vehicleId` — train unit number (stays stable across polls)
- `naptanId` — the station this prediction is for
- `lineId` — tube line identifier (`central`, `jubilee`, `victoria`, `northern`, etc.)
- `direction` — `inbound` (towards central) or `outbound`
- `timeToStation` — **seconds** until this train is expected to arrive
- `expectedArrival` — absolute ISO 8601 timestamp of expected arrival
- `timestamp` — when this prediction was generated by TfL
- `modeName` — `tube`, `dlr`, `elizabeth-line`, `overground`

   What `lineId` values appear? (Oxford Circus serves Central, Bakerloo, and Victoria.)

2. Run the same command 3 times, 30 seconds apart.
   - Does the same `vehicleId` appear across multiple polls?
   - Does `timeToStation` decrease by roughly 30 each time? Or is the change irregular?
   - Do prediction IDs (`id`) stay stable for the same vehicle, or do they change?

3. Answer these questions:
   - What does it mean when a train disappears between two consecutive polls?
   - What values appear in `modeName`? Are all of them "tube"?
   - Are there predictions with `timeToStation = 0`? What does that mean?
   - Is `direction` always populated? Is `bearing` ever populated?
   - What is the largest `timeToStation` value you see? Is a 45-minute prediction reliable?
   - What does `currentLocation` contain? Is it always a station name, or can it be something else?
   - Does `destinationNaptanId` ever differ from `destinationName` in an unexpected way?

4. Compare King's Cross (`940GZZLUKSX`) to Embankment (`940GZZLUEMB`).
   King's Cross has 6 lines; Embankment has 4. How does the number of arrivals differ?

## Phase B: Producer and Ingestion

### producer.py

Write a Python script that:
- Polls all 10 station endpoints **in parallel** using `concurrent.futures.ThreadPoolExecutor`
- For each poll, adds a `polled_at` field (unix timestamp) and a `polled_station` field to every record
- Writes all records from all stations in a single JSON file (one record per line)
  to `/tmp/data-engineering-at-scale/99-project/17-tfl-arrivals/raw/`
- File names: `poll_<unix_timestamp>.json`
- Prints after each poll: `Poll 5: 187 arrivals from 10 stations`
- Runs until stopped with Ctrl+C

> Using ThreadPoolExecutor to parallelise the 10 HTTP requests is the key design
> decision here. Fetching stations sequentially takes ~3 seconds; in parallel it
> takes ~0.5 seconds. This matters because the API updates every 30 seconds.

### ingestion_job.py

Write a PySpark batch job that:
- Reads all JSON files from the landing directory
- Parses `timestamp` and `expectedArrival` and `timeToLive` as `TimestampType`
- Adds `ingested_at` column (current timestamp)
- Writes to `raw-delta` using `mode("append")`

## Phase C: Cleansing Job (45 min)

### cleansing_job.py

Read from `raw-delta` and apply these validation rules:

### Data quality rules

| # | Field | Rule | rejection_reason |
|---|-------|------|-----------------|
| 1 | `id` | Not null | `null_prediction_id` |
| 2 | `naptanId` | Not null | `null_naptan_id` |
| 3 | `lineId` | Not null | `null_line_id` |
| 4 | `vehicleId` | Not null | `null_vehicle_id` |
| 5 | `timeToStation` | >= 0 | `negative_time_to_station` |
| 6 | `timeToStation` | <= 3600 (max 1 hour) | `implausible_time_to_station` |
| 7 | `modeName` | One of: `tube`, `dlr`, `elizabeth-line`, `overground`, `national-rail` | `unknown_mode` |
| 8 | `timestamp` | Not null | `null_prediction_timestamp` |

**Output:**
- Failing records + `rejection_reason` → `error-delta`
- Passing records → `valid-delta`
- Print a summary.

## Phase D: Business Analytics Job (90 min)

### business_job.py — Platform Headway Monitor

The **headway** is the time gap between two consecutive trains at the same platform.
A consistent headway means predictable service. A large headway after a short one
means bunching — trains arriving in clusters with long gaps between them.

Read from `valid-delta`.

### Business rules

**Step 1 — Compute per-platform headways:**

For each `(naptanId, lineId, direction)` group, within a **15-minute window**,
sort trains by `timeToStation` and compute the gap between consecutive values.

| Column | Description |
|--------|-------------|
| `naptanId` | Station |
| `lineId` | Line |
| `direction` | inbound/outbound |
| `window_start` | Start of the 15-minute window |
| `train_count` | Number of distinct trains in this window |
| `avg_headway_seconds` | Mean gap between consecutive trains |
| `max_headway_seconds` | Largest single gap (worst wait) |
| `min_headway_seconds` | Smallest gap (bunching indicator) |
| `bunching_flag` | `true` when `max_headway_seconds > 3 * min_headway_seconds` |

Write to `business-delta/platform_headways/`.

**Step 2 — Line service summary** (group by `lineId` and 1-hour window):

| Column | Description |
|--------|-------------|
| `lineId` | Tube line |
| `window_start` | Start of hour |
| `station_count` | Distinct stations with arrivals |
| `total_arrivals` | Total prediction records |
| `avg_time_to_station` | Mean `timeToStation` across all predictions |
| `top_destination` | Most frequent `destinationName` in this window |

Write to `business-delta/line_hourly_summary/`.
